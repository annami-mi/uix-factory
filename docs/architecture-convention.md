# Конвенция архитектуры фронтенда — шаблон фабрики

> Статус: шаблон v0.2 (переписан 2026-09-25 из конвенции конкретного B2B-проекта в переиспользуемую форму).
> Копируется в `docs/architecture-convention.md` каждого нового проекта на старте и дозаполняется разделом 0 и разделом 12 под этот проект. Ядро (разделы 1–11, 13–14) не переписывается заново каждый раз — меняются только пункты, отмеченные `[выбор проекта]`.
> UI-кит фабрики пока без названия — везде ниже используется плейсхолдер `@kit/ui` / `@kit/tokens`; при первом реальном подключении заменить на настоящее имя пакета во всех проектах разом (это и есть польза шаблона — не искать по каждому репо вручную).

Документ фиксирует **как устроен** фронтенд конкретного проекта и **как в нём принято писать новый код**. Это ядро вынесено из реального работающего кода (Clean Architecture по фичам, B2B-приложение с `client`+`admin`) — не абстрактная теория, а проверенный на масштабе паттерн. Часть решений — обязательное ядро фабрики, часть — решается заново для каждого проекта (раздел 0).

Уровни требований:
- **MUST** — обязательно, нарушение блокирует MR.
- **SHOULD** — по умолчанию делаем так; отступление объясняем в MR.
- **MAY** — допустимо по ситуации.

---

## 0. Что решить в начале ЭТОГО проекта (заполнить перед первой фичей)

Это единственный раздел, который переписывается с нуля для каждого нового приложения. Не начинать первую фичу, пока не заполнено.

| Решение | Варианты | Выбор в этом проекте |
|---|---|---|
| Нужен ли DI-контейнер на фичу (inversify) | Да (несколько реализаций порта, нужна подмена в тестах/по контексту) / Нет — только для landing/small-site веток, порт вызывается напрямую через фабричную функцию | — |
| Библиотека валидации форм | vuelidate / vee-validate + zod (выбрать одну, не смешивать — см. §12 базового проекта, где смешение — техдолг) | — |
| Server state | vue-query везде, где есть повторное использование/кэш, или только для справочников | — |
| Один composition root или несколько (`app`+`admin`, как в примере, либо только `app`) | Определяется продуктом — SaaS с ролями обычно 2, лендинг/сайт — 1 | — |
| Realtime | Нужен ли (centrifuge/websocket) с первого дня или добавляется по факту первой live-фичи | — |
| Базовые (не зависящие от прикладных) фичи проекта | Перечислить явно — они не должны зависеть от прикладных фич (§11) | — |
| Название пакетов UI-кита в этом проекте | `@kit/ui`, `@kit/tokens` (заменить, когда кит получит имя) | — |

Для первого подопытного приложения (SaaS-админка) — см. также `docs/roadmap.md` фабрики и ADR фабрики (`0001`–`0007`): кит и его токены уже спроектированы отдельно, эта конвенция описывает только код **приложения**, которое кит потребляет.

## 1. Стек и базовые решения

| Область | Решение | Статус |
|---|---|---|
| Фреймворк | Vue 3, `<script setup lang="ts">`, Composition API | ядро |
| Язык | TypeScript `strict` | ядро |
| Декораторы (inversify) | включены, только если в §0 выбран DI-контейнер | `[выбор проекта]` |
| Сборка | Vite | ядро |
| Composition root(ы) | `client`/`admin` из одной кодовой базы — пример; конкретный состав | `[выбор проекта]` |
| DI | inversify, контейнер на каждую фичу (`ContainerManager`) — если выбран в §0 | `[выбор проекта]` |
| Глобальное состояние | Pinia — только разделяемое состояние сессии, не серверные данные | ядро |
| Серверное состояние / кэш | TanStack Vue Query — там, где нужен кэш/повторное использование | ядро |
| HTTP | axios за абстракцией `HttpClient` + `BaseHttpRepository` | ядро |
| Realtime | centrifuge через отдельную фичу `messaging`, если выбран в §0 | `[выбор проекта]` |
| UI-кит | `@kit/ui`, токены `@kit/tokens` (фабричный кит, имя — TODO) | ядро фабрики |
| i18n | vue-i18n, локали лежат в каждой фиче (нужен, только если проект многоязычный) | `[выбор проекта]` |
| Валидация форм | одна библиотека, выбор — §0 | `[выбор проекта]` |
| Тесты | vitest + jsdom | ядро |
| Ошибки / мониторинг | Sentry (или аналог) через `LoggingService` | ядро |

**Архитектурный стиль:** Clean Architecture внутри вертикальных фич (feature-based modules). Каждая фича — самостоятельный модуль со слоями `domain → application → infrastructure / presentation` и публичным API в `index.ts`. Это ядро не зависит от масштаба проекта — маленький проект просто заводит меньше фич, а не отменяет слои внутри них (иначе к третьему реальному проекту накапливается тот же техдолг, что и в исходном примере, §12).

## 2. Структура верхнего уровня

```
src/
├── bootstrap.ts     # общий запуск приложения: DI (если есть), плагины, pinia, query, i18n, кит
├── app/             # основной composition root
│   ├── main.ts
│   ├── presentation/
│   │   ├── App.vue, components/ (layout-ы, хедер, футер)
│   │   ├── pages/        # страницы-композиции из нескольких фич
│   │   ├── router/       # сборка маршрутов, ROUTE_NAMES, guards
│   │   ├── i18n/         # сборка словарей всех фич (если есть i18n)
│   │   └── access/       # правила доступа уровня приложения
│   └── utils/            # init/clear сессии
├── admin/           # второй composition root — только если решено в §0
├── features/        # бизнес-фичи
└── shared/          # переиспользуемое ядро без бизнес-смысла конкретной фичи
```

### Правила уровней

| Модуль | Может импортировать | Не может импортировать |
|---|---|---|
| `app/` (и второй root, если есть) | `@features/<name>` (только публичный API), `@shared` | внутренности фич (`@features/x/presentation/...`) |
| `features/<x>` | `@shared`, публичный API других фич `@features/<y>` | root-приложения, внутренности других фич |
| `shared/` | внешние библиотеки | `@features/*`, root-приложения |

- **MUST** composition root(ы) — единственное место, где фичи «склеиваются» между собой в страницы, маршруты и словари.
- **MUST** `shared` не знает о фичах. Если утилите нужна бизнес-сущность — это не `shared`, а фича (или root).

## 3. Структура фичи

```
features/<featureName>/
├── index.ts                      # ПУБЛИЧНЫЙ API фичи
├── domain/
│   ├── entities/                 # сущности и их типы/enum-ы
│   ├── valueObjects/             # объекты-значения
│   ├── errors/                   # доменные ошибки (при необходимости)
│   └── types/
├── application/
│   ├── repositories/             # ИНТЕРФЕЙСЫ репозиториев (порты)
│   ├── useCases/                 # сценарии, по классу на сценарий
│   │   └── <subdomain>/          # группировка при большом кол-ве
│   ├── types/
│   │   ├── params.ts             # входные параметры use case / репозитория
│   │   ├── result.ts             # Result-типы
│   │   └── errors.ts             # прикладные ошибки фичи (наследники BaseError)
│   ├── events/                   # константы realtime-событий фичи (если есть realtime)
│   ├── strategies/                # стратегии (при необходимости)
│   └── services/                  # интерфейсы сервисов (при необходимости)
├── infrastructure/
│   ├── di/                       # только если в §0 выбран DI-контейнер
│   │   ├── types.ts              # Symbol-токены (расширяют shared TYPES)
│   │   ├── inversify.config.ts   # createContainer(parent)
│   │   └── index.ts              # getContainer(), реэкспорт TYPES
│   ├── dto/                      # контракты API (responses.ts, params.ts)
│   ├── mappers/                  # DTO ⇄ domain, ErrorMapper фичи
│   ├── repositories/              # HTTP<Name>Repository — реализации портов
│   ├── events/                    # declaration merging реестра событий (если есть realtime)
│   └── utils/
└── presentation/
    ├── pages/                    # страницы фичи (точки входа для роутера)
    ├── components/<Area>/        # компоненты, сгруппированные по экрану/области
    │   └── ui/                   # «глупые» подкомпоненты области
    ├── composables/              # use<Something> — связка UI и use case-ов
    │   └── admin/                # композаблы, нужные только во втором root (если есть)
    ├── stores/                   # Pinia-сторы (только если нужно разделяемое состояние)
    ├── queries/<resource>/       # vue-query: keys, fetcher, useXxxQuery, selectors
    ├── router/                   # маршруты фичи (если фича их отдаёт)
    ├── i18n/{index.ts, locales/ru.json}   # если есть i18n
    ├── utils/, constants/, assets/
```

- **MUST** слои `domain`, `application`, `infrastructure`, `presentation` называются именно так.
- **SHOULD** не создавать пустые папки «на вырост». Папка появляется вместе с первым файлом — это то же правило «абстракция после реального применения», что и в ките фабрики.
- **MUST** название фичи — `camelCase` существительное бизнес-области (`order`, `catalog`, `billing`).

## 4. Слои и направление зависимостей

```
presentation ──► application ──► domain
      │               ▲
      ▼               │ (реализует порты)
infrastructure ───────┘
```

| Слой | Отвечает за | Может зависеть от | Запрещено |
|---|---|---|---|
| `domain` | Бизнес-модель: сущности, value objects, enum-ы статусов, инварианты | только своего `domain`, типов-примитивов `@shared` | Vue, Pinia, axios, `application`, `infrastructure`, `presentation`, `Result` |
| `application` | Сценарии: use case-ы, порты репозиториев, params/result/errors | `domain`, `@shared` (`BaseUseCase`, `Result`, `BaseError`) | Vue, Pinia, axios, `infrastructure`, `presentation` |
| `infrastructure` | Реализация портов: HTTP, DTO, мапперы, DI (если есть) | `application`, `domain`, `@shared` | `presentation` |
| `presentation` | UI: компоненты, композаблы, сторы, queries, роуты, i18n | `application`, `domain`, `infrastructure/di` (только для получения зависимостей) | `infrastructure/mappers`, `infrastructure/dto`, `infrastructure/repositories`, прямой HTTP |

Ключевые правила:
- **MUST** domain «чистый»: ни одного импорта из фреймворков и внешних слоёв.
- **MUST** компоненты не ходят в API напрямую. Путь данных: `Component → composable/store/query → UseCase → Repository (порт) → HTTP-реализация`.
- **MUST** presentation берёт из infrastructure **только** способ получения зависимости (DI или фабричную функцию, см. §0). Мапперы и DTO в presentation не импортируются.
- **MUST** DTO не выходят за пределы `infrastructure`. Наружу — только доменные сущности и application-типы.

## 5. Публичный API фичи (`index.ts`) и импорты

- **MUST** внешний код (другие фичи, composition root) импортирует фичу только через `@features/<name>`.
- **MUST** внутри фичи — абсолютные алиасы на конкретный файл (`@features/order/presentation/composables/useOrder`). Относительные пути (`../`) и импорт собственного `index.ts` запрещены (риск циклов).
- **MUST** в `index.ts` экспортируется **минимум**, нужный потребителям: типы и id сущностей; страницы/крупные виджеты — через `defineAsyncComponent`/ленивую фабрику; публичные композаблы; маршруты фичи (если она их отдаёт); `messages` для i18n; прикладные ошибки, которые потребитель должен распознавать.
- **SHOULD** предпочитать `export type { … }` для типов — не тянет код в чужой бандл.
- **MUST NOT** экспортировать наружу репозитории, DTO, мапперы, DI-контейнер фичи. Исключение — общая модель, реально переиспользуемая несколькими фичами, — фиксировать явно в §12 как осознанное решение, а не тихий побочный эффект.
- Алиасы: `@features/*`, `@shared`, алиас для каждого composition root (`@app/*`, при наличии второго — `@admin/*`), `@kit/*` для токенов кита, если нужен прямой алиас.

## 6. Domain

- **MUST** сущности — классы с `readonly` полями и конструктором из объекта опций (`new Order({...})`). Изменение = создание нового экземпляра, а не мутация.
- **MUST** идентификаторы типизируются алиасами: `export type OrderUUID = string`. В сигнатурах используем алиас, а не `string`.
- **SHOULD** статусы и справочные значения — `enum` со строковыми значениями, совпадающими с API.
- **SHOULD** бизнес-правила, вычисляемые из состояния сущности, живут методами/геттерами сущности, а не в компонентах.
- **SHOULD** value object — неизменяемый класс с валидацией в конструкторе и методом `equals`.
- **MAY** ссылаться на **типы** других фич через `import type` из их публичного API. Импорт классов/логики чужого домена — сигнал, что граница фич проведена неверно.

## 7. Application

### 7.1 Use case
- **MUST** один сценарий = один класс `<Verb><Noun>UseCase` в файле с тем же именем.
- **MUST** реализует `BaseUseCase<Input, Output extends Result>` из `@shared`; единственный публичный метод `execute(input, options?)`.
- **MUST** зависимости (порты) приходят через конструктор. Use case не знает про DI-контейнер (если он есть), Vue и HTTP.
- **SHOULD** поддерживать отмену: пробрасывать `options.signal` (нужно для vue-query).
- **SHOULD** не делать «прокси»-use case ради формы, если сценарий действительно сводится к одному вызову — это допустимо; оркестрация нескольких репозиториев, проверка условий, агрегация — место именно здесь, а не в композабле. Решить в §0/§15 текущего проекта, можно ли для простого CRUD обращаться к репозиторию напрямую, минуя use case — и держаться выбранного правила единообразно.
- Реэкспорт всех use case-ов фичи — `application/useCases/index.ts`.

### 7.2 Порты репозиториев
- **MUST** интерфейсы репозиториев лежат в `application/repositories/<Name>Repository.ts` и называются `<Name>Repository`.
- **MUST** методы возвращают `Promise<Result<T>>` (типы из `application/types/result.ts`), принимают объект параметров из `application/types/params.ts`.

### 7.3 Result и ошибки
- **MUST** операции, которые могут завершиться ошибкой, **не бросают исключения**, а возвращают `Result<T>` (`success(data)` / `failure(errors)` из `@shared`).
- **MUST** потребитель проверяет `result.success` перед доступом к `result.data`.
- **MUST** ошибки — наследники `BaseError` с кодом из `as const`-объекта фичи.
- Системные ошибки показываются тостом централизованно в `BaseHttpRepository` — не дублировать тосты для них в композаблах.
- Исключение бросается только на границе с vue-query: `throw new ResultQueryError(result)` в fetcher-е.

### 7.4 Realtime-события (только если выбрано в §0)
- **MUST** имена событий фичи — константа в `application/events/index.ts`.
- **MUST** типизация полезной нагрузки — declaration merging реестра событий в `infrastructure/events/index.ts`.
- Подписка в UI — через композабл `use<Feature>Events()`, с обязательной отпиской.

## 8. Infrastructure

### 8.1 HTTP-репозиторий
- **MUST** класс `HTTP<Name>Repository implements <Name>Repository` (+ `@injectable()`, если выбран DI).
- **MUST** базовый путь и маппер ошибок передаются в `super(basePath, <Feature>ErrorMapper)`. Эндпоинты — в константе `API` в начале файла.
- **MUST** запросы — только через методы базового класса (`httpGet/httpPost/...`), они уже возвращают `Result` и обрабатывают ошибки. Прямой `axios` запрещён.
- **MUST** ответ маппится в домен **внутри репозитория**.

### 8.2 DTO
- **MUST** типы запросов/ответов API — в `infrastructure/dto/{responses,params}.ts`, суффикс `DTO` / `Response`.
- DTO описывают API «как есть». Даты — строки; превращение в `Date` — задача маппера.

### 8.3 Мапперы
- **MUST** класс `<Entity>Mapper` со статическими методами `fromDTO` / `toDTO`.
- **MUST** маппер — чистая функция без побочных эффектов и без обращения к сети/сторам.
- **SHOULD** на каждый нетривиальный маппер — unit-тест `<Mapper>.test.ts` рядом.
- **MUST** ошибки API фичи маппятся в `<Feature>ErrorMapper extends BaseErrorMapper`.

### 8.4 DI (только если выбран в §0)
- **MUST** у каждой фичи свой контейнер: `di/types.ts`, `di/inversify.config.ts` (`createContainer(parent)`), `di/index.ts` (`getContainer()`).
- **MUST** биндим **интерфейс** (порт) к реализации.
- Разные реализации для разных composition root выбираются по `context` в `createContainer(parent, context)`, а не условиями в компонентах.

Если DI **не** выбран (маленький проект) — зависимость получают фабричной функцией без контейнера, например `getOrderRepository(): OrderRepository`, с тем же правилом «биндим интерфейс, не класс».

## 9. Presentation

### 9.1 Композаблы — основной способ связать UI и логику
- **MUST** имя `use<Something>`, файл с тем же именем.
- **MUST** use case-ы создаются лениво и с кэшем (через `useCaseFactory` при наличии DI, либо простую мемоизацию), зависимости берутся единообразным для проекта способом (см. §0/§8.4).
- **SHOULD** состояние загрузки — через `useLoading()` (`isLoading`, `execute`), а не ручные `ref(true/false)`.
- **MUST** композабл не делает запросов при вызове (без скрытых авто-запросов и side-effect-ов) — загрузка стартует явным вызовом метода, `onMounted` компонента или `enabled` у query.
- **MUST** если композабл подписывается на события/таймеры — он сам и отписывается.
- **SHOULD** module-level `ref` как синглтон-состояние вне функции — не использовать; для разделяемого состояния есть Pinia-стор.

### 9.2 Выбор механизма состояния

| Нужно | Используем |
|---|---|
| Локальное состояние экрана | `ref/computed` в компоненте или композабле |
| Серверные данные с кэшем, пагинацией, повторным использованием на разных экранах | vue-query (`presentation/queries`) |
| Разделяемое клиентское состояние сессии (текущий пользователь, выбранный контекст) | Pinia-стор |
| Команды (создать, изменить, согласовать) | композабл + use case (или `useMutation`, если нужна инвалидация кэша) |

### 9.3 Pinia-сторы
- **MUST** файл `presentation/stores/<name>Store.ts`, экспорт `use<Name>Store`, id стора — имя фичи/сущности.
- **SHOULD** для нового кода — setup-синтаксис `defineStore('id', () => {...})`.
- **MUST** стор хранит доменные сущности, а данные получает через композабл/use case. Импорт мапперов и репозиториев из infrastructure в сторе запрещён.
- **MUST** если стор хранит данные пользователя — у него есть `clear()`/`$reset`, добавленный в общую процедуру очистки сессии.

### 9.4 Vue Query
Структура на ресурс:
```
queries/
├── constants.ts          # STALE_TIME_MS / GC_TIME_MS на ресурс
└── <resource>/
    ├── keys.ts           # фабрика ключей: resourceKeys.all(), .detail(...)
    ├── fetcher.ts        # use case → данные, либо throw ResultQueryError
    ├── selectors.ts       # преобразования для select (опционально)
    ├── use<Resource>Query.ts
    └── index.ts
```
- **MUST** ключи — только через фабрику `xxxKeys`, первый элемент — имя ресурса; все параметры, влияющие на ответ, входят в ключ.
- **MUST** fetcher вызывает use case (не репозиторий и не HTTP напрямую), пробрасывает `signal`.
- **MUST** время жизни кэша задаётся константами в `constants.ts` с комментарием, почему такое значение.
- **MUST** ключи данных, зависящих от авторизованного пользователя, начинаются с общего `scopeKey.auth()` — иначе не очищаются при логауте.

### 9.5 Компоненты и страницы
- **MUST** `pages/` — компоненты-точки входа роутера (`<Name>Page.vue`); собирают экран из компонентов фичи, получают параметры маршрута.
- **MUST** `components/<Area>/` группируются по экрану/области, «глупые» части — в `ui/`.
- **MUST** имя компонента — PascalCase с префиксом фичи.
- **MUST** порядок блоков SFC: `<template>` → `<script setup lang="ts">` → `<style scoped>` (или без стилей, если весь визуал — из кита).
- **MUST** props/emits типизируются интерфейсами (`defineProps<Props>()`, `defineEmits<Emits>()`).
- **MUST** в шаблоне нет сложной логики — выносим в `computed` или композабл; `v-for` с осмысленным `:key`.
- **SHOULD** базовые UI-элементы берутся из `@kit/ui`; свой компонент в `shared` — только если в ките нет аналога (и это повод сообщить в кит, а не молча дублировать — см. процесс фабрики).

### 9.6 Роутинг и доступ
- Маршруты собираются в `presentation/router` каждого composition root.
- **SHOULD** фича, у которой есть собственный набор страниц, отдаёт массив `<feature>Routes` и enum имён маршрутов. Root только подключает его.
- **MUST** доступ описывается декларативно (`meta.roles` или аналог), различный компонент для разных ролей — через фабрику компонента маршрута, а не `v-if` по роли внутри страницы.
- **MUST** имена маршрутов — константы, строковые литералы в `router.push` запрещены.
- Правила доступа, зависящие от нескольких фич, — чистые функции в `app/presentation/access` (или аналогичном месте).

### 9.7 i18n (только если выбрано в §0)
- **MUST** тексты фичи — в `presentation/i18n/locales/ru.json` с корневым ключом = имя фичи.
- **MUST** фича экспортирует `messages`; подключение словаря — строкой в сборке i18n composition root.
- **MUST** хардкод пользовательских строк в шаблоне/коде запрещён.

Если проект одноязычный — раздел не применяется, но правило «строки не хардкодятся в разметке произвольно» всё равно остаётся хорошей практикой для будущей локализации.

## 10. Shared

- `shared/application` — базовые типы (`Result`, `BaseError`, `BaseUseCase`, `Page`), интерфейсы сервисов (`LoggingService`, `NotifyService`, `TokenService`).
- `shared/infrastructure` — `HttpClient`, `BaseHttpRepository`, `BaseErrorMapper`, DI-инфраструктура (если есть), плагины (auth, logging, realtime), реализации сервисов.
- `shared/presentation` — компоненты без бизнес-логики, общие композаблы (`useLoading`, `useFiltersQuery`), директивы, queryClient, утилиты роутера.
- `shared/utils` — чистые функции-форматтеры и хелперы.
- **MUST** в `shared` попадает только то, что используется ≥ 2 фичами и **не содержит знания о конкретной бизнес-сущности**.
- **MUST** `shared` не импортирует фичи. Это правило легче держать с первого дня, чем чинить постфактум (см. эталонный пример, где это оказалось самым массовым нарушением — 38 импортов).

## 11. Взаимодействие фич

1. **Через публичный API** — импорт типов, страниц, композаблов из `@features/<name>`.
2. **Через события** — если выбран realtime, реестр расширяется фичами.
3. **Через композицию в composition root** — страница приложения собирает виджеты нескольких фич.

Правила:
- **MUST** граф зависимостей между фичами — ациклический. Если A нужен B, а B нужен A — общее выносится в третью фичу, в `shared` (если нет бизнес-смысла) или композиция поднимается в root.
- **SHOULD** «базовые» фичи проекта (перечислены в §0) не зависят от «прикладных».
- **SHOULD** межфичевые зависимости в `domain` — только `import type`.
