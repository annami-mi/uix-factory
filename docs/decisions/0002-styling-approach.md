# ADR-0002: Подход к стилизации

Статус: принято 2026-09-24

## Контекст

Нужна система, где: (1) тема меняется через значения токенов без правки компонентов, (2) glass и другой сложный арт-дирекшн пишутся обычным CSS, а не обходятся через утилитные классы, (3) компоненты остаются проверяемыми и лёгкими для AI-агента, который будет их писать и расширять.

## Решение

- **CSS custom properties + `<style scoped>` + `@layer`** (reset, tokens, base, components, sections, overrides). Без Tailwind в пакете `ui`.
- Приложения (эталонный лендинг и будущие клиентские проекты) могут использовать Tailwind поверх для быстрой раскладки страницы — но не внутри библиотеки компонентов. Пересмотреть, если это создаст два конфликтующих способа задавать одно и то же.
- **Container queries** — для секций и компонентов, которые должны реагировать на выделенное место, а не на весь viewport (карточки, toolbar, форма). **Media queries** — только в page shell (общая навигация, layout страницы).
- **Mobile-first**: `min-width` в media queries, базовые стили — для узкого экрана без переопределений сверху.
- Материал поверхности — через семантические токены с fallback, чтобы плоская тема не требовала правок компонента:

```css
.surface {
  background: var(--surface-bg);
  border: 1px solid var(--surface-border);
  backdrop-filter: var(--surface-backdrop, none);
  box-shadow: var(--surface-shadow, none);
}
```

- Брейкпоинты — константы, сгенерированные из токенов (в `@media` нельзя использовать `var()`), не хардкод в каждом файле.

## Альтернативы и почему отклонены

- **Tailwind в библиотеке** — держит компонент в разметке класс-строками, а не в семантике токена; сложнее гарантировать, что тема не завязана на конкретные utility-классы. Плюс два способа задавать один и тот же visual language (Tailwind config + токены) расходятся.
- **CSS Modules / SCSS** — не нужен дополнительный сборочный слой при уже достаточных Vue scoped styles и CSS-нативных возможностях (nesting, `@layer`, custom properties).
- **UnoCSS** — та же проблема, что Tailwind, просто другой синтаксис.

## Последствия

- Каждый компонент должен явно документировать, какие семантические токены он использует (роль, не хардкод) — фиксируется в `docs/components.md` на каждый компонент.
- Ревью нового компонента включает проверку: нет ли внутри hex-значений, spacing "на глаз", медиа-запросов, написанных не mobile-first.
