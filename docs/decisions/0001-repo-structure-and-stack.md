# ADR-0001: Структура репозитория и стек

Статус: принято 2026-09-24

## Контекст

Один разработчик, цель — фабрика для лендингов/сайтов/магазинов/SaaS. Нужна структура, которая не создаёт лишней инфраструктуры до появления второго реального применения, но не мешает вырасти в неё позже.

## Решение

- **pnpm workspaces**, без Turborepo/Nx на старте (оркестратор не окупается при 2–3 пакетах).
- Пакеты раздаются как исходники (`workspace:*`), без отдельной сборки/публикации до первого внешнего клиентского репозитория.
- Публичные сайты — **Nuxt 4** (SSG/prerender, SEO, server routes для форм). SaaS позже — **Vue 3 + Vite** (SSR не нужен).
- Структура:

```text
uix-factory/                  # сам кит — отдельный репозиторий
  CLAUDE.md
  docs/
    architecture.md
    tokens.md
    components.md
    sections.md
    figma-code.md
    roadmap.md
    audit.md
    decisions/
  packages/
    tokens/       # DTCG JSON → CSS переменные + TS, по темам
    ui/            # base CSS, layout, компоненты, формы-паттерны
    sections/      # секции лендинга + их Content-типы
```

**Клиентские/эталонные проекты — отдельные репозитории** (уточнено 2026-09-24, см. также ADR-0004), не `apps/*` внутри этого монорепо. Кит подключается к ним как внешняя зависимость. Первый эталонный проект (`reference-landing`, Nuxt SSG) заводится отдельным репозиторием намеренно — это единственный способ по-настоящему проверить, что граница пакета работает, а не полагаться на то, что `workspace:*` всё равно даёт удобный доступ к внутренностям.

- Правило двух применений: код выделяется в общий пакет только после второго реального использования. Исключение — foundations/tokens/ui, которые заведомо переиспользуются с первого дня.

## Mobile-first как архитектурное ограничение

Мобильный экран — основной сценарий использования продуктов фабрики, десктоп — расширение. Это не только CSS-правило (см. ADR-0002), но и требование к структуре компонентов:

- Компонент проектируется и тестируется сначала на 360–390px, десктопные варианты добавляются после.
- Дефолтные размеры интерактивных элементов — комфортные для тача (см. `audit.md`), компактные варианты — не дефолт.
- Эталонный проект (`apps/reference-landing`) верстается и проверяется в первую очередь на мобильной ширине.

## Альтернативы и почему отклонены

- Turborepo/Nx — лишняя конфигурация при текущем объёме кода.
- Сборка и приватный npm-реестр сразу — нет второго потребителя, который бы это оправдал.
- Один плоский проект вместо monorepo — не разделяет ui/sections/tokens по скорости изменения и не даёт эталонному сайту жить отдельно от библиотеки.

## Последствия

- Способ подключения кита к клиентским проектам (без реестра, до появления второго клиента) и вопрос отдельных пакетов на каждую стилистику — вынесены в ADR-0004, чтобы не раздувать этот документ при пересмотре.
