# ADR-0003: Источник истины токенов и процесс с Figma

Статус: принято 2026-09-24

## Контекст

Figma-тариф — Starter: нет modes, Dev Mode, Code Connect, публикации библиотек. Локальные переменные внутри файла доступны и уже используются осмысленно (semantic/primitive разделение, стекло как переключаемая роль поверхности). Нужно решить, где именно живёт "истина" по значениям токенов и как строится процесс добавления новых стилистик при этих ограничениях.

## Решение

1. **Figma — авторская поверхность для первой (флагманской) стилистики "Жидкое стекло".** Здесь ценно визуальное чутьё (свет, blur, слои) — рисуется руками, как уже начато (Button, Field).
2. **Код — источник истины начиная с момента переноса.** Токены читаются из Figma через MCP (`get_variable_defs`), оформляются как DTCG JSON в `packages/tokens/source/`, оттуда генерируются CSS-переменные и TS-типы. После переноса правки токенов делаются в коде; ручной перенос обратно в Figma — по явному решению, не автоматически.
3. **Вторая и последующие стилистики — токен-first, без полной отрисовки в Figma.** Поскольку на Starter нельзя переключать modes в одном файле, а дублирование фреймов под каждую стилистику дорого без Dev Mode, компонентная структура не меняется — меняются только значения токенов, подбираются напрямую в Storybook. Figma для этих стилистик — не более чем референс-палитра/moodboard, не полная матрица состояний.
4. **Синхронизация Figma ↔ код — ручная**, через `docs/figma-code.md` (component-map: имя Figma-компонента → Vue-компонент → node-id → статус). Без Code Connect это единственный вариант на Starter; при переходе на Organization/Enterprise — отдельный ADR.
5. **Соглашение об именовании токенов** (закрывает нестыковки из аудита):
   - Цвет: `color/<role>/<state>` (уже так).
   - Пространство/размер: `space/*`, `size/*`, `radius/*` (уже так).
   - Типографика: единый префикс `type/<role>/<size>` (например `type/label/md`, `type/body/sm`, `type/caption`) — заменяет разнобой `label/md` / `body/md` / `caption` без группы.
   - Материал поверхности: `surface/<role>/<state>` для bg/border/shadow/backdrop одной роли, чтобы тема могла подставлять `none` там, где эффекта нет.
   - Токены без ясной роли (пример — `White: #FAFAFA`) в Figma переименовываются или удаляются до переноса в код; в код переносится только то, что имеет понятную роль.

## Альтернативы и почему отклонены

- **Полная отрисовка каждой стилистики в Figma** — на Starter означает ручное дублирование всей матрицы состояний под каждую тему; дорого и не масштабируется на 3+ стилистики.
- **Автоматическая двусторонняя синхронизация** — недоступна без Code Connect; и в целом создаёт риск незаметной перезаписи (см. общий риск "Drift Figma/код" в исследовании).
- **Ждать перехода на Professional ради modes** — не блокирует старт: modes решают только удобство просмотра нескольких стилистик внутри одного файла Figma, а не саму возможность делать разные темы. Пересмотреть, если ручной процесс на практике окажется слишком медленным.

## Последствия

- Перед переносом каждого нового Figma-компонента: проверить именование (см. пункт 5), найти и объяснить/переименовать "осиротевшие" токены вроде `White`.
- `docs/figma-code.md` заводится вместе с первым перенесённым компонентом (Button) и обновляется при каждом новом компоненте.
- Если ручное сопровождение станет узким местом (много рассинхронов, забытые обновления) — рассмотреть переход на Professional ради modes/Dev Mode отдельным решением, а не по умолчанию.
