# ADR-0008: Каталог вариантов компоновки (Sections + Patterns) и Look Recipe

Статус: принято 2026-09-25

## Контекст

До этого решения "разный внешний вид" в ките означал только смену токенов (ADR-0005: `data-theme` × `data-scheme`) — цвет, материал, форма. Это дёшево, но не покрывает то, что реально делает продукт непохожим на другой: другую компоновку сайдбара, другую подачу карточки, другую структуру Hero.

Прямое требование: **сегодня собрать 2 разные админки** — одна и та же бизнес-логика (фичи, домен, use case-ы — см. `architecture-convention.md`), но разный внешний вид и "вайб", чтобы для конечного пользователя это выглядело как два разных продукта. То же самое нужно и для лендингов: каталог секций (Hero, Advantages, Testimonials, Pricing, FAQ, CTA), из которого выбираешь под проект, а не рисуешь заново.

В `CLAUDE.md` уже есть правило под это: «Не создавать новый компонент под каждую композицию — контракт контента один, композиционно разные варианты — отдельные компоненты с общим типом контента». Не хватало: (1) явного места, где такие варианты каталогизируются, (2) механизма выбрать набор вариантов сразу для всего приложения одним решением, а не поштучно на каждом экране.

## Решение

### 1. Два каталога композиционных вариантов, не один

- **`packages/sections`** (уже в дереве ADR-0001) — роли для лендингов/сайтов: `Hero`, `Advantages`, `Testimonials`, `Pricing`, `FAQ`, `CTA`, `Header`, `Footer`. У каждой роли — один контент-контракт (`HeroContent`, `TestimonialsContent`, ...) и 2–3 варианта-компонента (`HeroSplit`, `HeroCentered`, `HeroWithProof`).
- **`packages/ui/src/patterns`** (новое) — композитные куски для SaaS/админок: `AppShell` (компоновка сайдбар/топбар), `Sidebar` (rail/expanded/grouped), `Card` (image-top/data-dense/minimal), `DataTableRow` (density/striped/compact), `ChartCardLayout` (labeled/sparkline-heavy/minimal). Живёт внутри `@uix/ui`, не отдельным пакетом — по тому же правилу ADR-0004: пакет дробим только после реальной необходимости, а не заранее.
- **Не более 2–3 вариантов на роль/паттерн на старте.** Комбинаторику не плодим — тот же принцип, что ADR-0005 уже применил к темам. Новый вариант добавляется в каталог по факту реального проекта или обоснованного референса, не "про запас".
- **MUST — ни один новый вариант не проектируется без реального референса.** Ни Claude Code, ни эта сессия не придумывают компоновку "из головы" — источник всегда конкретный существующий интерфейс (протокол референсов: 10–20 мин, максимум 6 фрагментов, обязательно URL/автор + дата + что именно берём как принцип). Причина жёсткая, не формальная: сгенерированная без опоры на реальный образец компоновка систематически скатывается в усреднённый "нейрослоп" — узнаваемо AI-сгенерированный вид без характера, даже если технически валиден и проходит все проверки кита. Референс не обязан быть новым для каждого варианта — можно опираться на уже сохранённые в личной базе референсов (см. `refero.design` и подобные), но опора должна быть предъявима, а не подразумеваема.
- Задача Claude Code при реализации варианта — **воспроизвести структуру и характер конкретного референса**, адаптировав под контент-контракт и токены кита, а не "сделать что-то в похожем стиле". Промпт на новый вариант обязан включать сам референс (ссылку/скриншот/описание) как вход, не как вдохновение.

### 2. Look Recipe — один объект, переключающий вид всего приложения

```ts
// пример формы, не финальный API
export interface LookRecipe {
  theme: "glass" | "neutral";
  scheme: "light" | "dark";
  appShell: "sidebar-rail" | "sidebar-expanded" | "topbar";
  card: "data-dense" | "minimal" | "image-top";
  dataTableRow: "compact" | "comfortable";
  chartCard: "labeled" | "sparkline";
  // для проектов с публичными страницами — то же самое для секций:
  hero?: "split" | "centered" | "with-proof";
  testimonials?: "grid" | "carousel";
}
```

- **MUST** Look Recipe подключается **только на composition root** (`app/`, `admin/` — см. `architecture-convention.md` §2). Фичи, домен, application и infrastructure про него не знают вообще.
- Composition root использует recipe явно при сборке страницы: `<AppShell variant={recipe.appShell}><Sidebar variant={recipe.appShell === "topbar" ? undefined : "rail"} /></AppShell>`. Не рантайм-магия с provide/inject "угадай тему" — конкретный проект один раз выбирает recipe при сборке, а не переключает на лету (переключение на лету — это уже `data-theme`/`data-scheme`, отдельная, более лёгкая ось).
- Два разных админки = два разных `look.ts` в двух разных composition root, при полностью одинаковых `features/*`. Это и есть ответ на «оставить логику, поменять стилистику»: граница ровно там же, где граница фич и presentation в конвенции архитектуры — recipe **часть presentation**, не глубже.
- Несколько готовых Look Recipe можно держать как именованные пресеты (`recipes/compact-dark.ts`, `recipes/airy-light.ts`) — стартовые точки, которые можно и нужно точечно переопределять (`{ ...compactDark, card: "minimal" }"`), а не только выбирать целиком. Это и есть «конструктор + мой выбор»: выбираешь пресет и донастраиваешь по одному паттерну, а не собираешь с нуля.

### 3. Что нужно упаковать в ките, чтобы это заработало уже сегодня

Честная проверка того, что реально готово, а что нет:

| Нужно | Статус |
|---|---|
| Токены: 2 стилистики × 2 схемы | ✅ есть (ADR-0005) |
| `AppShell`/`Sidebar` хотя бы в 2 вариантах | ❌ нет вообще — ни одного варианта, есть только отдельные примитивы |
| `Card` в 2–3 вариантах | ❌ есть один канонический `Card` (ADR-0006), вариантов компоновки нет |
| `DataTableRow`/`ChartCardLayout` в 2–3 вариантах | ❌ есть один канонический вариант каждого (ADR-0006/0007) |
| Механизм Look Recipe (тип + пример сборки в composition root) | ❌ не описан нигде до этого ADR |

Вывод: **два разных админки сегодня в один клик не выйдет** — сначала нужно превратить существующие "один канонический вариант" компоненты ADR-0006/0007 в каталог из 2–3 вариантов там, где это реально влияет на "вайб" (в первую очередь `AppShell`/`Sidebar` и `Card` — это определяет впечатление сильнее всего), плюс сам механизм Look Recipe. Это осязаемая, небольшая задача — не пересборка кита с нуля.

## Альтернативы и почему отклонены

- **Один универсальный конфигурируемый компонент на всё** (`Sidebar` с 15 пропами на любую комбинацию) — воспроизводит именно ту проблему, которую критиковали в исходной B2B-конвенции (§12, смешение стилей и растущая матрица условий внутри одного файла). Разные структурные варианты — разные компоненты с общим контрактом, не пропы-переключатели.
- **Рантайм-провайдер темы вида, читающий Look Recipe из контекста Vue во всех компонентах** — компонент тогда обязан знать про recipe, что нарушает базовое правило кита («компонент не знает, какая активна стилистика»). Recipe остаётся решением уровня сборки, не рантайм-состоянием.
- **Отдельный npm-пакет на каждый паттерн** — то же самое решение, что уже принято в ADR-0004 для стилистик, применяется и здесь: не дробим до реальной необходимости.
- **Дать Claude Code спроектировать вариант без референса ("что-то стильное в стиле glass/neutral")** — отклонено явно (см. MUST выше). Результат такого промпта отличим на глаз как типовой AI-сгенерированный интерфейс, и это ровно то, чего кит должен избегать по своей исходной цели — узнаваемого, а не усреднённого продукта.

## Последствия

- Roadmap (шаги 9–11) переформулируются: не «сделать Header/Hero/Footer для одного лендинга», а «собрать каталог по 2–3 варианта на ключевые роли (Sections + Patterns), выбрать/собрать Look Recipe для эталонного лендинга и для первой админки из него».
- Storybook получает верхнеуровневую группировку `Sections/*` и `Patterns/*` рядом с `Components/*`.
- `docs/figma-todo.md` и `docs/components.md` дополняются по мере появления вариантов.
- Промпт для Claude Code на следующий шаг должен явно ссылаться на этот ADR, а не молча плодить очередной единственный "канонический" вариант компонента.
