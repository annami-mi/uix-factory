# ADR-0004: Как кит подключается к проектам и нужны ли отдельные пакеты на каждую стилистику

Статус: принято 2026-09-24 (первая часть), вторая часть — открытый вопрос, см. ниже

## Вопрос 1: как кит физически попадает в клиентский проект

### Контекст

`uix-factory` — отдельный репозиторий (ADR-0001). Нужен способ подключить `@uix/ui`/`@uix/tokens` в проект клиента (начиная с `reference-landing`), не создавая инфраструктуру публикации раньше, чем она реально понадобится.

### Решение

- До второго реального клиентского проекта — подключение через `file:`-зависимость (локальный путь до собранного пакета) или git-зависимость на конкретный коммит/тег, без реестра.
- `packages/ui` и `packages/tokens` должны собираться в дистрибутив (а не раздаваться как исходники внутри workspace, как было в первой версии ADR-0001) — иначе `file:`/git-зависимость не будет содержать рабочий JS/CSS. Это меняет пункт ADR-0001 "пакеты раздаются как исходники (`workspace:*`)": сборка нужна с первого клиентского проекта, публикация в реестр — нет.
- Версионирование — простой `0.x.y` вручную в `package.json`, без changesets/CI-релизов, пока не появится второй клиент, которому нужно будет обновляться независимо от первого.
- Приватный npm-реестр (или GitHub Packages и т.п.) — заводится, когда появится второй реальный клиентский репозиторий, которому нужно подключать кит тем же способом, что и первому. До этого мы просто не знаем, какие ограничения реестра реально важны.

### Реализация (2026-09-26)

- Дистрибутив — один пакет `mi-kit` (`packages/kit`), а не три: проекту нужен кит целиком, три версии `@uix/*` разъезжались бы. Подпути: `mi-kit` (компоненты), `mi-kit/charts`, `mi-kit/tokens`, `mi-kit/styles.css`, `mi-kit/font-pairs/*`, `mi-kit/tokens.json`.
- `@uix/*` остаются внутренними пакетами монорепо с исходниками — Storybook и тесты работают как раньше; `packages/kit/scripts/build.mjs` собирает из них JS (Vite lib, зависимости наружу), CSS (шрифты fontsource копируются в `dist/assets`, url() относительные) и типы (vue-tsc).
- `"private": true` в `packages/kit/package.json` — защита от случайной публикации: имя без scope в npm всегда публичное. Приватный реестр (платный npm со scope `@<user>/mi-kit` или GitHub Packages `@annami-mi/mi-kit`) — отдельное решение; до него — `pnpm pack` и установка из `.tgz`.
- CI собирает пакет на каждый push — сломанный дистрибутив виден сразу.

### Альтернативы и почему отклонены

- **Публикация в приватный реестр сразу** — оправдана только при ≥2 потребителях; сейчас добавляет CI, авторизацию и релизный процесс без второго проекта, который бы это подтвердил.
- **Оставить кит внутри монорепо как `apps/*`** — не проверяет реальную границу пакета (общий workspace прощает много того, что сломается при настоящей внешней зависимости: неявные side-effect импорты, забытые exports, дублирование зависимостей).

## Вопрос 2: нужен ли базовый пакет + отдельные пакеты на каждую стилистику

### Контекст

Предложена альтернативная модель: `@uix/ui-core` (поведение, доступность, структура — без визуала) как базовый пакет, и отдельные `@uix/ui-glass`, `@uix/ui-light-neutral` и т.д., которые "накручивают" визуал поверх базового. Это отличается от текущей модели: один пакет `@uix/ui`, темы переключаются через `data-theme` и CSS-переменные из `@uix/tokens`.

### Моя оценка: пока нет, но идея не отклоняется, а откладывается по конкретному условию

То, что предлагается, — по сути, headless-ядро + skin-пакеты, паттерн, которым реально пользуются зрелые мульти-брендовые дизайн-системы. Направление разумное само по себе. Но у нас уже есть более дешёвая версия того же принципа: `packages/ui` — это и есть "базовый пакет" (структура, поведение, a11y), а каждый файл в `packages/tokens/source/themes/*.json` — это и есть "стилистика, накрученная поверх базы", просто на уровне значений токенов, а не на уровне отдельных npm-пакетов с собственным кодом компонентов.

Разница между двумя моделями — не "делаем базовый пакет или нет" (он уже есть), а **где проходит граница переиспользования: на уровне значений (токены) или на уровне кода компонента (отдельный пакет со своей версией `Button.vue`)**.

Пока не заводить отдельные пакеты на стилистику, потому что:

1. У нас одна отрисованная стилистика и один черновик второй — недостаточно данных, чтобы понять, действительно ли им нужна разная структура компонента, а не просто разные значения. Правило двух применений здесь работает вдвойне: разделять код компонента по стилистикам стоит делать после того, как токен-модель реально не справится хотя бы дважды.
2. N пакетов на N стилистик — это N точек публикации, N version bump'ов при каждом изменении API компонента, и риск, что `@uix/ui-glass` и `@uix/ui-light-neutral` разъедутся поведением (разные обработчики событий, разная разметка) — то самое "три анимационные библиотеки вместо одной", только на уровне компонентов.
3. Если стилистике нужен визуальный элемент, которого нет у другой (например, декоративный слой преломления света у стекла) — это чаще решается слотом или необязательным под-компонентом внутри одного `@uix/ui` (`<Surface><template #decoration>...</template></Surface>`), а не форком всего компонента в отдельный пакет.

### Условие, при котором пересматриваем

Если при реализации второй стилистики (light-neutral) или третьей (когда появится) окажется, что для неё нужна **другая DOM-структура одного и того же компонента**, а не только другие значения токенов — и это происходит не один раз, а стабильно на нескольких компонентах — тогда действительно стоит выделять `@uix/ui-core` + skin-пакеты. Зафиксировать этот сигнал в `docs/roadmap.md` при обнаружении, не откладывать молча.

### Что действительно стоит сделать уже сейчас в эту сторону

Даже оставаясь в модели "один пакет + токены", полезно писать `packages/ui` так, будто он уже разделён на core/skin внутри себя: структура и доступность компонента — в основном шаблоне, всё визуально-специфичное — только через CSS-переменные и (где нужно) именованные слоты. Тогда переход к отдельным пакетам, если он понадобится, будет рефакторингом, а не переписыванием.

## Последствия

- Обновить `docs/decisions/0001-repo-structure-and-stack.md` (сделано) — убрать формулировку "раздаются как исходники", заменить на "собираются в дистрибутив с первого клиентского проекта".
- В промпт для Claude Code на следующий шаг (Field/Input) добавить требование: если для второй стилистики понадобится другая разметка, а не только токены — остановиться и вынести это как открытый вопрос сюда, а не решать самостоятельно.
