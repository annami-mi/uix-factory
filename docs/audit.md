## Компонент: Button (frame 127:566, "Buttons")

Состав: `Button` (primary/secondary × default/hover/pressed/focused/disabled/loading), `IconButton` (те же состояния), 4-фазный spinner, 5 outline-иконок (send, arrow-up-right, search, close, chevron down/up).

Токены (полный список см. в `packages/tokens/source/reference/button.json` — TODO при переносе):

- Разделение primitive/semantic уже выстроено: `space/*`, `size/*`, `radius/full`, `font/size/*`, `font/line-height/*` — примитивы; `color/surface/*`, `color/accent/*`, `color/text/*`, `color/icon/*`, `color/state/focus` — семантика.
- **Стекло — часть семантики поверхности, не отдельный декоративный слой.** У каждого состояния accent-кнопки — тройка `color/accent/glass` (bg) / `color/accent/glass-border` / `color/accent/shadow`, и отдельные `-hover`/`-pressed` варианты каждой. У secondary-кнопки — `color/surface/default,hover,pressed` + `color/glass-border/default`. Это подтверждает архитектурное решение: материал поверхности = роль (`surface-interactive` и т.п.) → набор из bg/border/shadow, которые тема просто подставляет разными значениями.
- Форма: `radius/full` = 999 → капсула. Использован одинаково и для Button, и для Field (см. ниже) — сквозной визуальный характер, не случайность.

## Компонент: Field / Input / Select (frame 149:723, "Inputs")

Состав: `field` (компактный, search-подобный, 6 состояний), `input` (с Label + Hint text, 6 состояний), `select` (то же + 7-е состояние `opened`).

Новые токены: `color/icon/secondary`, `color/text/secondary`, `color/text/tertiary`, `color/status/danger` (для error — не переиспользует accent, это отдельная статусная роль), `color/glass-border/subtle`, типографика `body/md`, `body/sm`, `label/sm`.

Наблюдения:

- Текстовая лестница `text/primary → secondary → tertiary → disabled` уже выстроена под связку label/value/hint/placeholder — переносится в `FormField` без изменений.
- Error-состояние красит border, label и hint одним статусным токеном — паттерн правильный, переиспользуем в FormField.
- `state=opened` у Select не покрыт общей 6-состояний схемой Button/IconButton — это осмысленное расширение (у кнопки не бывает "открыт"), не баг.

## Frame "glass code" (128:738) — 4 nav-тайла (Home/Folder/Group/Menu)

Единственное место, где встречается отдельный "glass-код" помимо Button/Field. `get_variable_defs` на этом фрейме вернул **пустой набор переменных** — ни одно значение (фон, бордер, blur) не привязано к переменной. Это значит:

- Стеклянный эффект здесь, вероятно, захардкожен на уровне слоя (заливка/blur как локальные значения), а не выражен через те же токены `surface/*`, что в Button/Field.
- Переносить в код визуально "на глаз" со скриншота, а не как задокументированные значения — то же ограничение, что и с неподтверждёнными `backdrop`-значениями в `packages/tokens/source/themes/glass.json` (см. ADR-0003, `docs/claude-code-prompt-step-3.md`).
- Компонентной ценности для v1 кита фрейм не добавляет (это композиция, не новый примитив) — сам паттерн навигационного тайла не заводится отдельным компонентом сейчас (правило "абстракция после второго применения", см. `CLAUDE.md`), но токены поверхности стоит свести к уже существующим `surface/accent`/`surface/neutral`, если/когда этот паттерн понадобится реально.

## Проблемы неймспейсов и нейминга (закрыть до Code Connect / переноса в токены)

1. **Типографика без единого префикса.** Button: `label/md`, `caption`. Field: `body/md`, `body/sm`, `label/sm`, `caption`. Цвет и spacing сгруппированы (`color/...`, `space/...`), типографика — нет. → в токенах ввести `type/label/md`, `type/body/md`, `type/caption` и т.д.
2. **`"White": "#FAFAFA"`** встречается в обоих файлах без семантической группы и понятного назначения. Нужно найти слой-источник и переименовать в `color/…` с ролью, либо убрать, если это случайный локальный стиль.
3. **Focused-состояние Input/Field вообще не имеет обводки** — проверено вручную (не хардкод, а отсутствие решения). Это реальный пробел, а не деталь переноса: без видимого фокуса компонент не пройдёт собственный QA-критерий "видимый focus" (см. `CLAUDE.md`) и WCAG 2.4.7. **Решение:** не переносить это состояние из Figma как есть. В коде Input/Select/Textarea получают focus-индикатор на токене `color/state/focus` (он уже есть и используется в Button) — например обводка/outline при `:focus-visible`. Затем это же решение возвращается в Figma как правка макета, а не наоборот.
4. **`type=secondary, size=md, state=state11`** (IconButton) — похоже на случайное имя варианта вместо реального состояния. Переименовать в Figma перед фиксацией маппинга.
5. Порядок свойств в именах вариантов не унифицирован (`size=md, state=focused` vs `type=secondary, size=md, state=focused`) — мелочь, но мешает автоматическому парсингу при будущей автоматизации.

## Что подтвердилось из первоначального плана

- Разделение Foundations/Components/Patterns/Sections остаётся верным — ничего пересматривать не пришлось.
- Материал поверхности как переключаемая роль (bg/border/shadow/backdrop) — уже так спроектировано в самой Figma, осталось формализовать в CSS-токенах с fallback (`var(--surface-backdrop, none)`), чтобы плоские темы не требовали правок компонента.
- Капсульная форма — сквозной признак стилистики "Жидкое стекло", стоит зафиксировать как именованный shape-recipe, а не переиспользовать `radius/full` бездумно в других местах.

## Приоритет: mobile-first (зафиксировано 2026-09-24)

Кит проектируется в первую очередь под мобильный экран, десктоп — расширение. Это влияет на аудит и на ADR:

- Уже увиденные размеры кнопок/полей (`size/44`, `size/48`) сами по себе укладываются в комфортный touch target (см. WCAG 2.2 таргет 24×24 с исключениями; наш внутренний ориентир — 44–48px, это уже есть в токенах) — хороший знак, ничего пересматривать не нужно.
- При дальнейшей отрисовке компонентов в Figma и переносе в код: по умолчанию брать вариант размера, комфортный для тача (`md`, не `sm`), а компактные варианты — осознанное исключение для плотных десктопных экранов (таблицы SaaS), а не дефолт.
- Storybook: дефолтный viewport в `preview.ts` — мобильный (360–390px), десктоп — переключение, а не наоборот.
- CSS-стратегия: media queries пишутся mobile-first (`min-width`), а не override сверху вниз от десктопа.
- При аудите новых экранов Figma отдельно смотреть hit area, а не только визуальный размер иконки/текста внутри контрола.
